# HW12 – временные ряды: temporal split, baseline-модели и GRU-прогноз

## 1. Кратко: что сделано
- **Датасет**: `S12-hw-dataset.csv` — почасовые данные, целевая переменная `target`.
- **Прогнозировалось**: следующее значение временного ряда (горизонт = 1 шаг).
- **Split**: temporal разделение 70% train / 15% validation / 15% test по времени.
- **Сравниваемые подходы**: 
  - `B1` — naive-last (прогноз = последнее значение)
  - `B2` — moving-average с окном 7
  - `B3` — Ridge-регрессия на лаговых и rolling-признаках
  - `R1` — GRU-сеть на оконном представлении
- **Лучший подход**: `B3 (Ridge)` с `val_MAE = 5.03`. Простая линейная модель превзошла GRU благодаря стабильности и отсутствию переобучения на небольшом объёме данных.

## 3. Данные и постановка задачи
- **Датасет**: `S12-hw-dataset.csv`
- **Целевая колонка**: `target`
- **Частота временного ряда**: почасовая (24 наблюдения в день)
- **Горизонт прогноза**: 1 шаг вперёд
- **Размер датасета**: 4320 наблюдений (~180 дней)
- **Диапазон дат**: 2025-01-01 00:00:00 → 2025-06-29 23:00:00
- **Дополнительные внешние признаки**: отсутствуют
- **Комментарий**: ряд демонстрирует выраженную суточную и недельную сезонность, присутствуют пиковые выбросы. Прогноз осложняется нестационарностью и высокой волатильностью в отдельные периоды.

## 4. Temporal split и признаки

### 4.1. Разбиение по времени
- **Как выполнен split**: последовательное разделение по индексу после сортировки по дате.
- **Доли**: train = 70% (3024 строки), validation = 15% (648 строк), test = 15% (648 строк).
- **Почему random split некорректен**: при случайном перемешивании модель получает доступ к «будущим» данным при обучении, что нарушает причинно-следственную связь и даёт завышенную оценку качества.

### 4.2. Признаки для baseline-моделей
- **Лаги**: `lag_1`, `lag_7`, `lag_14`, `lag_28`
- **Rolling-признаки**: `rolling_mean_7`, `rolling_std_7`, `rolling_mean_14` (с `shift(1)` для исключения утечки)
- **Календарные признаки**: `dayofweek`, `month`, `day`, `hour` + синус/косинус-кодирование для цикличности
- **Обработка пропусков**: удаление строк с NaN после создания лагов; для val/test пропуски заполнялись последним значением из train
- **Масштабирование**: `StandardScaler`, обученный только на train, применён к val и test

## 5. Модели и эксперименты (B1, B2, B3, R1)

| Модель | Описание |
|--------|----------|
| **B1 (`naive-last`)** | Прогноз = значение `lag_1` (предыдущий час) |
| **B2 (`moving-average`)** | Прогноз = `rolling_mean_7` (среднее за последние 7 часов) |
| **B3 (`ridge-lag-features`)** | Ridge-регрессия (alpha=1.0) на всех признаках после масштабирования |
| **R1 (`gru-forecast`)** | Однослойная GRU (hidden=32), окно=7, Adam, lr=1e-3, 50 эпох |

**Дополнительно**:
- Основная метрика: `MAE`
- Дополнительные метрики: `RMSE`, `MAPE`
- `window_size` для GRU: 7
- Batch size: 32
- Максимальное число эпох: 50
- Optimizer: Adam
- Learning rate: 1e-3
- Сохранение лучшей модели: по минимальному `val_MAE` через `state_dict()`

## 7. Анализ
Наивный baseline (B1) оказался достаточно сильным, что типично для рядов с высокой автокорреляцией: следующее значение часто близко к предыдущему. Однако он не учитывает сезонность, поэтому уступает более сложным методам. Скользящее среднее (B2) сработало хуже, так как окно 7 часов не соответствует суточной периодичности данных. Ridge-регрессия (B3) показала лучший результат благодаря способности взвешенно комбинировать лаги разной длины и календарные признаки, при этом оставаясь устойчивой к шуму. GRU-модель (R1) не превзошла линейный baseline: вероятно, объёма данных (~3000 обучающих примеров) недостаточно для стабильного обучения рекуррентной сети, а также могла возникнуть проблема с масштабированием таргета или подбором гиперпараметров. Тренд и сезонность в ряде заметны, и именно признаки, кодирующие их (lag_7, hour_sin/cos), дали основной вклад в качество B3. Утечки данных могли возникнуть при неправильном расчёте rolling-статистик (без shift), но в коде это учтено. Выбор модели по validation, а не по test, принципиален: test используется только один раз для финальной оценки, чтобы избежать «подгонки» под тестовые данные. Наиболее показательными оказались ошибки в часы пик — все модели систематически недооценивали резкие всплески.

## 8. Итоговый вывод
В качестве базового подхода для подобной задачи я бы взял **Ridge на лаговых признаках**: он прост, интерпретируем, быстро обучается и даёт стабильное качество. Простого baseline на признаках достаточно, когда ряд имеет выраженную линейную зависимость от прошлого и сезонности, а данных немного. Переход к GRU/нейросетям имеет смысл при большом объёме данных, сложных нелинейных зависимостях или необходимости многошагового прогноза. Главное, что я понял про валидацию временных рядов: **никогда не перемешивать данные**, всегда сохранять хронологический порядок и проверять, что признаки не содержат информации из будущего.
